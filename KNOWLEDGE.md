# KNOWLEDGE.md — правила значимости изменений для `tracker`

Этот файл определяет, какие изменения в diff (см. `SKILL.md`, раздел
«Сравнение с предыдущим прогоном») стоят уведомления, а какие — шум,
который нужно отбросить. Правила применяются к diff **после** того, как
он посчитан по `url`, и **до** того, как он попадёт в ответ пользователю
(и позже — в Telegram).

Важно: эти правила фильтруют только то, что показывается как diff. Сам
JSON-файл прогона в `tracker-data` всегда хранит точные значения,
которые вернул `extract-price`, без округлений и фильтрации — обрезается
только слой уведомлений.

## Ошибка извлечения — это не изменение цены

Первое и самое важное правило, раньше всех остальных: **ошибка
извлечения страницы (`status: "error"` у элемента прогона — см.
`SKILL.md`, «Схема хранения») никогда не должна попадать в diff как
изменение**. Это не порог значимости — это вопрос корректности данных:
недоступная страница не отличается по форме от «цена стала `null`» или
«рассрочку убрали», но по смыслу это совершенно разные вещи —
«неизвестно» и «изменилось» нельзя путать.

`tracker` уже решает это на шаге построения diff (см. `SKILL.md`,
«Сравнение с предыдущим прогоном», шаг 5): пара сравнивается по полям
**только когда `status` обеих сторон — `"ok"`**; если у текущей или
предыдущей записи `status: "error"`, товар в diff вообще не попадает —
ни как `changed`, ни как `added`/`removed` — а уходит в отдельный
список проблем извлечения. Из-за этого весь остаток этого файла ниже
может считать, что раз пара дошла до сравнения полей — у обеих сторон
`status: "ok"`, и `regular_price` в такой паре **всегда** число, никогда
`null`. Единственное легитимное `null` в успешной паре — это
`sale_price` (означает «скидки нет»), см. следующий раздел.

## Порог изменения цены

- Значимым считается изменение `regular_price` или `sale_price`, если
  оно **≥ 1%** от предыдущего значения (порог общий для обоих полей,
  считается независимо друг от друга).
- Формула: `|to - from| / from * 100 >= 1`. Если `|to - from| / from *
  100 < 1` — изменение незначимое, отбрасывается (это и есть
  «колебание цены на копейки/сатанги»: сайт мог обновить цену на пару
  единиц валюты без реального пересмотра стоимости).
- Правило применяется, только когда **и `from`, и `to` — числа**
  (сравнение "было число → стало другое число"). Для `sale_price`
  переход `null ↔ число` — легитимный случай, разбирается отдельно
  ниже (появление/исчезновение скидки). Для `regular_price` перехода
  `null ↔ число` в принципе быть не должно — по инварианту из раздела
  «Ошибка извлечения» выше, `regular_price` в паре, дошедшей до
  сравнения полей, всегда число с обеих сторон; если ты видишь здесь
  `regular_price: null`, это значит, что фильтрация ошибок извлечения
  в `tracker` не сработала — это баг выше по цепочке, а не сигнал
  «цена пропала», и такую пару всё равно нельзя показывать как
  изменение цены.
- Если `from == 0` (цена была нулевой — по сути ошибка данных), любое
  изменение считается значимым: делить на ноль нельзя, а нулевая цена
  сама по себе подозрительна.
- Порог 1% — значение по умолчанию для этой ниши (jib.co.th, цены в
  целых батах). При добавлении ниши с другой типичной ценой и
  валютой это число можно скорректировать здесь же, ничего другого в
  скилле менять не нужно.

## Появление и исчезновение скидки (`sale_price`)

- `sale_price` был `null`, стал числом → **скидка появилась** — это
  значимое изменение **всегда**, независимо от размера скидки (даже
  скидка на 0.5% всё равно означает, что товар впервые попал в акцию —
  сам факт важнее величины).
- `sale_price` было числом, стал `null` → **скидка закончилась** —
  тоже значимо всегда, тем же рассуждением в обратную сторону.
- Если `sale_price` было числом и осталось числом, но изменилось —
  это уже не «появление/исчезновение», а обычное изменение цены:
  применяется порог 1% из раздела выше.

## Изменение рассрочки (`has_credit`)

- `has_credit` — булево поле, у него нет «маленьких» изменений: любой
  переход `true → false` или `false → true` значим всегда, порог
  здесь неприменим в принципе.

## Появление нового и пропажа старого товара

- Товар есть в текущем прогоне, но его не было в предыдущем
  (`status: "added"`) — значимо всегда. Это либо новый товар,
  добавленный в список отслеживания, либо (в будущем, если список
  перестанет быть статическим) товар, впервые появившийся в наличии.
- Товар был в предыдущем прогоне, но пропал из текущего
  (`status: "removed"`) — значимо всегда: либо его убрали из списка
  отслеживания, либо (в будущем) он пропал со стороны магазина.
- Для `added`/`removed` понятие «порога» не применяется — сам факт
  появления/пропажи важнее любых числовых значений.
- `added` не путать с ошибкой извлечения на новом товаре: если url
  впервые появился в таблице отслеживания, но именно в этом прогоне
  `extract-price` для него вернул `status: "error"`, `tracker` не
  создаёт diff-запись `added` — товар уходит в список проблем
  извлечения и станет `added` только в первом прогоне, где для него
  реально прочитана цена (см. `SKILL.md`, шаг 5).

## Алгоритм применения к diff

Вход — «сырой» diff из `SKILL.md` (список элементов
`{ id, url, status, changes[] }`, где `status` — `changed` / `added` /
`removed`, а `changes` — список `{ field, from, to }` для `regular_price`
/ `sale_price` / `has_credit`). Товары с ошибкой извлечения (`status:
"error"` элемента прогона) в этот список уже не входят — `tracker`
отфильтровал их на шаге построения diff (см. раздел «Ошибка извлечения»
выше), это правило их не касается.

Для каждого элемента сырого diff:

1. Если `status` — `added` или `removed`: элемент значим целиком,
   переноси его в итоговый diff без изменений.
2. Если `status` — `changed`: пройдись по `changes` этого элемента и
   для каждого `{ field, from, to }` реши, значимо ли изменение:
   - `field == "sale_price"` и (`from == null` или `to == null`) →
     значимо (появление/исчезновение скидки);
   - `field == "has_credit"` → значимо (булево, порога нет);
   - `field` в (`"regular_price"`, `"sale_price"`) и `from`/`to` —
     оба числа → значимо, если `|to - from| / from * 100 >= 1`
     (или `from == 0`), иначе — отбрасывается;
   - других полей в `changes` быть не должно (diff по контракту
     `extract-price` состоит только из этих трёх полей).
3. Если после фильтрации у элемента остался хотя бы один пункт в
   `changes` — оставь элемент в итоговом diff, но только с теми
   `changes`, что прошли фильтр (отброшенные не показывай).
4. Если после фильтрации `changes` элемента опустел — элемент целиком
   не входит в итоговый diff: это был шум (например, единственное
   изменение — цена сдвинулась на доли процента), и по товару в этом
   прогоне сообщать нечего.

Итоговый (отфильтрованный) diff — это то, что идёт в ответ пользователю
и (в будущем) в уведомление в Telegram. Пустой итоговый diff — валидный
результат: значит, все изменения в сыром diff были шумом, и в этом
прогоне уведомлять не о чем.

## Примеры

| было | стало | вывод |
|---|---|---|
| `regular_price: 13500` | `regular_price: 13550` (+0.37%) | незначимо, отброшено |
| `regular_price: 13500` | `regular_price: 13000` (-3.7%) | значимо, `{field: "regular_price", from: 13500, to: 13000}` |
| `sale_price: null` | `sale_price: 12900` | значимо (появилась скидка), независимо от суммы |
| `sale_price: 2090` | `sale_price: null` | значимо (скидка закончилась) |
| `has_credit: true` | `has_credit: false` | значимо (рассрочку убрали) |
| товара не было → появился | — | значимо (`status: "added"`) |
| товар был → пропал | — | значимо (`status: "removed"`) |
| страница не открылась в этом прогоне (`status: "error"`) | — | не изменение — в diff вообще не попадает, товар уходит в список проблем извлечения |
