# tracker

## Назначение

`tracker` — обёртка над скиллом `extract-price` для пакетного обхода
списка отслеживаемых товаров. За один прогон он:

1. обходит зашитый список товаров и получает цену каждого через
   `extract-price`;
2. собирает результат в таблицу прогона;
3. через GitHub MCP находит и читает предыдущий сохранённый прогон в
   `zxvfc/tracker-data` (если он есть) и считает diff — что изменилось по
   каждому товару;
4. применяет к diff правила значимости из корневого `KNOWLEDGE.md`,
   отбрасывая шум вроде колебания цены на копейки, и оставляет только
   то, о чём стоит уведомить;
5. делегирует форматирование короткой сводки саб-агенту `tg-summary`
   (модель Haiku — дешёвая задача не требует основной модели) и
   отправляет её в Telegram через корневой `send.py`;
6. сохраняет новый прогон как отдельный JSON-файл в том же репозитории —
   через GitHub MCP, отдельным коммитом, без локального `git
   clone`/`git push`.

## Сценарий выполнения

`tracker` не парсит цены сам — вся эта логика уже инкапсулирована в скилле
`extract-price`, и `tracker` её не дублирует, а переиспользует.

Для каждой строки таблицы выше, по порядку:

1. Вызови скилл `extract-price`, передав ему `url` этой строки как
   единственный вход.
2. Получи от него объект `{ status, regular_price, sale_price, has_credit,
   error? }` (актуальный контракт `extract-price` — см. его `SKILL.md`).
   **Не путай этот `status` с полем `status` diff-записи** (`changed` /
   `added` / `removed`, см. следующий раздел) — это разные объекты,
   значение здесь только `"ok"` или `"error"`.
3. Собери из этого элемент прогона (см. схему в следующем разделе),
   добавив `id`, `name`, `url` из таблицы выше и текущее время как
   `checked_at`:
   - при `status: "ok"` — перенеси `regular_price`/`sale_price`/
     `has_credit` как есть, добавь `"status": "ok"`;
   - при `status: "error"` — `regular_price`, `sale_price`, `has_credit`
     запиши как `null` (не подставляй `false` для `has_credit` — это не
     «рассрочки нет», а «неизвестно»), добавь `"status": "error"` и
     `"error"` с причиной из ответа `extract-price`.

Обработай так весь список целиком за один запуск. Если `extract-price`
для какого-то URL вернул `status: "error"` — это не сбой всего прогона:
зафиксируй элемент товара как есть (см. выше) и продолжи обход остальных
товаров. Один неудачный URL не должен прерывать весь прогон — и, что
важно, дальше по пайплайну (diff, правила значимости, Telegram) он
обрабатывается отдельно от настоящих изменений цены, а не наравне с
ними — см. следующий раздел.

## Схема хранения (согласована с `zxvfc/tracker-data`)

- Один прогон — один файл `YYYY-MM-DD.json` (дата прогона, UTC) в корне
  репозитория `zxvfc/tracker-data`.
- Повторный прогон в тот же день **перезаписывает** файл этого дня (не
  создаёт новый).
- Список прогонов получается листингом файлов репозитория — имена
  сортируются лексикографически, что совпадает с хронологическим порядком.

Содержимое файла:

```json
{
  "run_at": "2026-08-12T10:00:00Z",
  "niche": "видеокарты и игровая периферия (jib.co.th)",
  "currency": "THB",
  "items": [
    {
      "id": "asus-dual-rtx5060-8gb-oc",
      "name": "ASUS Dual GeForce RTX 5060 8GB GDDR7 OC Edition",
      "url": "https://www.jib.co.th/web/product/readProduct/76790/...",
      "status": "ok",
      "regular_price": 13500,
      "sale_price": null,
      "has_credit": true,
      "checked_at": "2026-08-12T10:00:03Z"
    },
    {
      "id": "amd-ryzen-5-9600",
      "name": "AMD Ryzen 5 9600 (6C/12T, 3.8-5.2GHz, AM5)",
      "url": "https://www.jib.co.th/web/product/readProduct/76890/...",
      "status": "error",
      "regular_price": null,
      "sale_price": null,
      "has_credit": null,
      "error": "HTTP 404",
      "checked_at": "2026-08-12T10:00:07Z"
    }
  ]
}
```

Поля верхнего уровня:

- `run_at` — момент начала прогона, ISO 8601 UTC (`...Z`). Дата из этого
  поля (UTC) — это и есть `YYYY-MM-DD` в имени файла.
- `niche` — фиксированная строка `"видеокарты и игровая периферия
  (jib.co.th)"`, описывающая список товаров выше.
- `currency` — фиксированная `"THB"` (все цены на jib.co.th — в тайских
  батах).
- `items` — по одному элементу на товар, в том же порядке, что в таблице
  выше; поля `id`/`name`/`url` берутся из таблицы, `status` /
  `regular_price` / `sale_price` / `has_credit` (и `error`, если он
  есть) — из ответа `extract-price`, `checked_at` — момент, когда для
  этого товара получен ответ `extract-price` (ISO 8601 UTC).
  - `status: "ok"` — цены получены, все три поля — реальные данные.
  - `status: "error"` — извлечь данные не удалось (страница не
    открылась, цена не найдена и т.п.); `regular_price`/`sale_price`/
    `has_credit` — `null`, это не содержательный ответ, а «неизвестно»,
    и **не должно** трактоваться как «цены/скидки/рассрочки не стало»;
    `error` — краткая причина сбоя из ответа `extract-price`. Сам файл
    прогона хранит эту неопределённость как есть — фильтрация от «шума
    ошибок» происходит на следующем шаге (diff), не здесь.

## Сравнение с предыдущим прогоном (diff)

Перед тем как сохранить новый прогон, найди прогон, с которым его можно
сравнить, и посчитай diff. Всё это — через GitHub MCP, без локального
клонирования.

1. Получи список файлов в корне `tracker-data` вызовом
   `mcp__github__get_file_contents` (`owner: "zxvfc"`, `repo:
   "tracker-data"`, `path: "/"`). Каждый файл вида `YYYY-MM-DD.json` —
   отдельный сохранённый прогон.
2. Из полученных имён отбери файлы `YYYY-MM-DD.json` с датой **строго
   раньше** даты текущего прогона (сравнивай имена как строки —
   лексикографический порядок `YYYY-MM-DD` совпадает с хронологическим).
   Если сегодняшний файл уже существует (повторный запуск в тот же
   день) — он в это сравнение не входит: это не прошлый прогон, а версия,
   которую вот-вот перезапишут.
3. Возьми из отобранных файлов последний по дате — это **предыдущий
   прогон**. Если отбирать нечего (файлов нет вовсе, или есть только
   сегодняшний) — прошлых прогонов ещё нет, это первый запуск. Сравнивать
   не с чем: пропусти шаги 4–6, отметь в ответе пользователю «первый
   прогон, сравнивать не с чем» и переходи сразу к сохранению.
4. Прочитай найденный файл вызовом `mcp__github__get_file_contents`
   (`path` — его имя) и распарси JSON — это `previous.items`. Если у
   записи товара в `previous.items` вообще нет поля `status` (файл
   записан до появления этого поля в схеме) — считай, что у неё
   `status: "ok"`: раньше все элементы прогона были успешными по
   умолчанию, это просто более старая версия той же схемы.
5. Посчитай diff между `previous.items` и `items` текущего прогона,
   сопоставляя товары **по `url`**. Прежде всего: **ошибка извлечения —
   это не изменение цены**, и в diff как изменение попасть не должна ни
   при каких условиях. Проверяй в этом порядке:

   1. **Текущая запись товара — `status: "error"`.** Не сравнивай ни с
      чем и не включай в diff — ни как `changed`, ни как `added`
      (даже если url впервые появился в таблице отслеживания и его ещё
      не было в `previous.items`). Данных за этот прогон нет — это не
      «цена/скидка/рассрочка пропала» и не «новый товар с ценой»,
      а «неизвестно». Вместо diff-записи добавь товар в отдельный
      список **проблем извлечения** (id, name, url, `error`) — он идёт
      в ответ пользователю (см. ниже), но не в diff, не через фильтр
      значимости `KNOWLEDGE.md` и не в сводку Telegram.
   2. Иначе (текущая запись — `status: "ok"`) смотри, был ли этот url в
      `previous.items`:
      - **url есть в `previous.items`, и там тоже `status: "ok"`** —
        сравни `regular_price`, `sale_price` и `has_credit` по
        отдельности; в diff попадают только реально изменившиеся поля,
        с парой `from`/`to`; если ни одно поле не изменилось — в diff
        товар не включай (`status: "changed"`, только если `changes`
        не пуст);
      - **url есть в `previous.items`, но там был `status: "error"`** —
        не сравнивай и не включай в diff: предыдущие значения
        ненадёжны, сравнивать не с чем (для этого товара это как
        первый прогон — просто зафиксируй его текущие данные,
        следующий прогон уже сравнит корректно);
      - **url нет в `previous.items` вовсе** — это товар, добавленный в
        отслеживание (`status: "added"`).
   3. **url есть только в `previous.items`** (в текущем прогоне товара
      нет вовсе — его убрали из таблицы отслеживания) — товар убрали
      (`status: "removed"`), независимо от того, какой у него был
      `status` в предыдущей записи.

   (Здесь и далее в этом разделе `status` diff-записи — `changed` /
   `added` / `removed` — не путай со `status` элемента прогона —
   `ok` / `error`, который разобран в пункте 1 и до сравнения полей не
   доходит.)
6. Полученный на шаге 5 diff — «сырой»: он содержит вообще все различия,
   включая незначительные колебания цены (например, на доли процента).
   Прежде чем показывать diff пользователю, примени к нему правила
   значимости из `KNOWLEDGE.md` (порог изменения цены, трактовка
   появления/исчезновения скидки и рассрочки, добавленных/пропавших
   товаров) и получи итоговый diff — только то, о чём действительно стоит
   уведомить. Незначимые изменения (порог не пройден) в итоговый diff не
   попадают; если у товара в `changes` не осталось ни одного значимого
   поля — товар целиком выпадает из итогового diff.

Формат diff (как сырого, так и итогового после фильтрации по
`KNOWLEDGE.md` — структура одна и та же, отличается только набор
элементов/полей) — список объектов, по одному на товар с изменениями:

```json
[
  {
    "id": "xbox-wireless-controller-doom-dark-ages",
    "url": "https://www.jib.co.th/web/product/readProduct/76835/...",
    "status": "changed",
    "changes": [
      { "field": "sale_price", "from": null, "to": 2290 }
    ]
  },
  {
    "id": "new-item-slug",
    "url": "https://www.jib.co.th/web/product/readProduct/.../...",
    "status": "added"
  }
]
```

Если итоговый (отфильтрованный по `KNOWLEDGE.md`) diff получился пустым —
это валидный результат двух разных ситуаций, различай их в ответе:
предыдущего прогона не было вовсе («первый прогон, сравнивать не с
чем») или прогон был, но все различия оказались незначимым шумом
(«изменений, о которых стоит уведомить, нет»).

## Сводка и отправка в Telegram

Выполняется после того, как посчитан итоговый (отфильтрованный по
`KNOWLEDGE.md`) diff, и до сохранения нового прогона.

Форматирование текста — простая задача, для которой не нужна мощная (и
дорогая) модель. Эту часть `tracker` делегирует саб-агенту `tg-summary`
(модель — Haiku, задан в `.claude/agents/tg-summary.md`), у которого
только одна работа — превратить список значимых изменений в аккуратный
короткий текст. Основная модель (`tracker`) занимается логикой: собирает
вход для саб-агента и отправляет то, что он вернул.

1. Собери вход для саб-агента — сам итоговый diff почти готов, не хватает
   только цены для `added`/`removed` (диff их не хранит). Для каждой
   записи собери объект:
   - `status: "changed"` → `{ name, status, changes }` — `changes` как
     есть из diff (`{ field, from, to }`);
   - `status: "added"` → `{ name, status, price }`, где `price` —
     `sale_price` товара в **текущем** прогоне, если он не `null`, иначе
     `regular_price` (найди сам товар в `items` текущего прогона по
     `url` из diff-записи);
   - `status: "removed"` → `{ name, status, price }`, тем же способом,
     но по товару из **предыдущего** прогона (`previous.items`).

   `name` — из таблицы отслеживаемых товаров (для `changed`) или из
   `items`/`previous.items` (для `added`/`removed`).
2. Вызови саб-агента `tg-summary` (инструмент `Agent`,
   `subagent_type: "tg-summary"`), передав ему в промпте
   собранный на шаге 1 список (может быть пустым) и `currency`
   текущего прогона (`"THB"`). Правила оформления (эмодзи, длина строк,
   формулировки под тип изменения, ровно `Значимых изменений цен нет`
   при пустом списке) уже описаны в самом саб-агенте — не дублируй их
   здесь и не переформулируй заново.
3. Получи от саб-агента готовый текст — используй его как есть, без
   правок. `tracker` не молчит ни при пустом diff, ни при непустом:
   какой бы текст ни вернул саб-агент, он всегда отправляется.
4. Отправь этот текст через корневой `send.py`, вызвав его как отдельный
   процесс: `python3 send.py "<текст>"`. Текст — **один** аргумент; при
   переносах строк передавай его так, чтобы они сохранились (например,
   через переменную оболочки в двойных кавычках), не разбивай сообщение
   на несколько вызовов. Учётные данные (`TELEGRAM_BOT_TOKEN`,
   `TELEGRAM_CHAT_ID`) скрипт сам берёт из окружения или из корневого
   `.env` — `tracker` их не запрашивает и никуда не подставляет
   напрямую.
5. Если `send.py` завершился с ошибкой (нет credentials, Telegram
   недоступен и т.п.) — не прерывай весь прогон: отметь в ответе
   пользователю, что отправка в Telegram не удалась (и почему), и всё
   равно переходи к сохранению прогона — сами данные важнее одного
   уведомления.
6. Если вызов саб-агента не удался (например, недоступен) — не блокируй
   прогон: собери тот же текст сам, по тем же смысловым правилам
   (см. `.claude/agents/tg-summary.md`), отправь его и отметь в
   ответе пользователю, что сводку пришлось собрать основной моделью, а
   не саб-агентом.

## Сохранение прогона в tracker-data через GitHub MCP

Выполняется после расчёта diff и отправки сводки в Telegram. Репозиторий
и ветка фиксированы: owner `zxvfc`, repo `tracker-data`, branch `main`.
Запись — это обычный вызов GitHub MCP, который сам создаёт коммит на
GitHub; локальный `git clone`/`git push` для этого не нужен и
использоваться не должен.

1. Собери JSON-документ по схеме выше и посчитай имя файла
   `YYYY-MM-DD.json` из даты `run_at` (UTC).
2. Проверь, существует ли уже файл с этим именем в репозитории — вызови
   `mcp__github__get_file_contents` (`owner: "zxvfc"`, `repo:
   "tracker-data"`, `path: "YYYY-MM-DD.json"`).
   - Если файл существует — запомни его `sha` из ответа (он понадобится
     для перезаписи).
   - Если файл не найден (404) — это первый прогон за день, `sha` не
     нужен.
3. Запиши файл вызовом `mcp__github__create_or_update_file`:
   - `owner: "zxvfc"`, `repo: "tracker-data"`, `branch: "main"`;
   - `path: "YYYY-MM-DD.json"`;
   - `content` — JSON-документ из шага 1 (человекочитаемый, с отступами);
   - `sha` — из шага 2, если файл уже существовал (без него обновление
     существующего файла будет отклонено); если файла не было — поле не
     передавай;
   - `message` — короткое сообщение коммита, например `tracker: прогон за
     2026-08-12`.

Это разовый коммит в `tracker-data` на каждый прогон (или перезапись
коммитом поверх файла этого же дня — при повторном запуске в тот же
день).

## Формат результата прогона (ответ пользователю)

Помимо коммита в `tracker-data`, верни пользователю:

1. итоговую таблицу прогона — одна строка на товар, не по одному товару за
   раз (для `status: "error"` — прочерк вместо цен, не `null`, чтобы
   визуально не путать с легитимным `sale_price: null`):

   | id | name | status | regular_price | sale_price | has_credit |
   |---|---|---|---|---|---|
   | asus-dual-rtx5060-8gb-oc | ASUS Dual GeForce RTX 5060 8GB GDDR7 OC Edition | ok | 13500 | null | true |
   | xbox-wireless-controller-doom-dark-ages | Microsoft Xbox Wireless Controller — DOOM: The Dark Ages | ok | 2590 | null | true |
   | logitech-g923-trueforce-racing-wheel | Logitech G G923 TRUEFORCE Racing Wheel (PS/PC) | ok | 12900 | null | true |
   | amd-ryzen-5-9600 | AMD Ryzen 5 9600 (6C/12T, 3.8-5.2GHz, AM5) | error | — | — | — |

2. итоговый (отфильтрованный по правилам значимости из `KNOWLEDGE.md`)
   diff с предыдущим прогоном: список изменений, о которых стоит
   уведомить (или явная отметка «первый прогон, сравнивать не с чем» /
   «изменений, о которых стоит уведомить, нет»);
3. **проблемы извлечения** — товары, для которых в этом прогоне
   `extract-price` вернул `status: "error"` (id, name, url, `error`),
   отдельным списком от diff (или явная отметка «проблем нет», если
   список пуст). Это не изменения цены и в Telegram-сводку не попадают —
   только в ответ пользователю здесь;
4. текст сводки, отправленной в Telegram, и результат отправки (успех
   или ошибка `send.py`);
5. имя файла `tracker-data`, в который записан этот прогон (например,
   `2026-08-12.json`), и имя файла, с которым сравнивали (если сравнение
   было).
