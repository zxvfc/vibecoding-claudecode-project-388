# tracker

## Назначение

`tracker` — обёртка над скиллом `extract-price` для пакетного обхода
списка отслеживаемых товаров. За один прогон он:

1. обходит зашитый список товаров и получает цену каждого через
   `extract-price`;
2. собирает результат в таблицу прогона;
3. через GitHub MCP находит и читает предыдущий сохранённый прогон в
   `zxvfc/tracker-data` (если он есть) и считает diff — что изменилось по
   каждому товару;
4. применяет к diff правила значимости из `KNOWLEDGE.md` (см. рядом с
   этим файлом), отбрасывая шум вроде колебания цены на копейки, и
   оставляет только то, о чём стоит уведомить;
5. сохраняет новый прогон как отдельный JSON-файл в том же репозитории —
   через GitHub MCP, отдельным коммитом, без локального `git
   clone`/`git push`.

В будущем сюда добавится отправка уведомлений об изменениях в Telegram.

## Сценарий выполнения

`tracker` не парсит цены сам — вся эта логика уже инкапсулирована в скилле
`extract-price`, и `tracker` её не дублирует, а переиспользует.

Для каждой строки таблицы выше, по порядку:

1. Вызови скилл `extract-price`, передав ему `url` этой строки как
   единственный вход.
2. Получи от него объект `{ regular_price, sale_price, has_credit }`.
3. Собери из этого элемент прогона (см. схему в следующем разделе),
   добавив `id`, `name`, `url` из таблицы выше и текущее время как
   `checked_at`.

Обработай так весь список целиком за один запуск. Если `extract-price` для
какого-то URL вернул `null`-объект (страница недоступна, цена не найдена и
т.п.) — зафиксируй это как есть в элементе этого товара (числа — `null`,
`has_credit: false`) и продолжи обход остальных товаров. Один неудачный
URL не должен прерывать весь прогон.

## Схема хранения (согласована с `zxvfc/tracker-data`)

- Один прогон — один файл `YYYY-MM-DD.json` (дата прогона, UTC) в корне
  репозитория `zxvfc/tracker-data`.
- Повторный прогон в тот же день **перезаписывает** файл этого дня (не
  создаёт новый).
- Список прогонов получается листингом файлов репозитория — имена
  сортируются лексикографически, что совпадает с хронологическим порядком.

Содержимое файла:

```json
{
  "run_at": "2026-08-12T10:00:00Z",
  "niche": "видеокарты и игровая периферия (jib.co.th)",
  "currency": "THB",
  "items": [
    {
      "id": "asus-dual-rtx5060-8gb-oc",
      "name": "ASUS Dual GeForce RTX 5060 8GB GDDR7 OC Edition",
      "url": "https://www.jib.co.th/web/product/readProduct/76790/...",
      "regular_price": 13500,
      "sale_price": null,
      "has_credit": true,
      "checked_at": "2026-08-12T10:00:03Z"
    }
  ]
}
```

Поля верхнего уровня:

- `run_at` — момент начала прогона, ISO 8601 UTC (`...Z`). Дата из этого
  поля (UTC) — это и есть `YYYY-MM-DD` в имени файла.
- `niche` — фиксированная строка `"видеокарты и игровая периферия
  (jib.co.th)"`, описывающая список товаров выше.
- `currency` — фиксированная `"THB"` (все цены на jib.co.th — в тайских
  батах).
- `items` — по одному элементу на товар, в том же порядке, что в таблице
  выше; поля `id`/`name`/`url` берутся из таблицы, `regular_price` /
  `sale_price` / `has_credit` — из ответа `extract-price`, `checked_at` —
  момент, когда для этого товара получен ответ `extract-price` (ISO 8601
  UTC).

## Сравнение с предыдущим прогоном (diff)

Перед тем как сохранить новый прогон, найди прогон, с которым его можно
сравнить, и посчитай diff. Всё это — через GitHub MCP, без локального
клонирования.

1. Получи список файлов в корне `tracker-data` вызовом
   `mcp__github__get_file_contents` (`owner: "zxvfc"`, `repo:
   "tracker-data"`, `path: "/"`). Каждый файл вида `YYYY-MM-DD.json` —
   отдельный сохранённый прогон.
2. Из полученных имён отбери файлы `YYYY-MM-DD.json` с датой **строго
   раньше** даты текущего прогона (сравнивай имена как строки —
   лексикографический порядок `YYYY-MM-DD` совпадает с хронологическим).
   Если сегодняшний файл уже существует (повторный запуск в тот же
   день) — он в это сравнение не входит: это не прошлый прогон, а версия,
   которую вот-вот перезапишут.
3. Возьми из отобранных файлов последний по дате — это **предыдущий
   прогон**. Если отбирать нечего (файлов нет вовсе, или есть только
   сегодняшний) — прошлых прогонов ещё нет, это первый запуск. Сравнивать
   не с чем: пропусти шаги 4–6, отметь в ответе пользователю «первый
   прогон, сравнивать не с чем» и переходи сразу к сохранению.
4. Прочитай найденный файл вызовом `mcp__github__get_file_contents`
   (`path` — его имя) и распарси JSON — это `previous.items`.
5. Посчитай diff между `previous.items` и `items` текущего прогона,
   сопоставляя товары **по `url`**:
   - для каждого url, встретившегося в обоих прогонах — сравни
     `regular_price`, `sale_price` и `has_credit` по отдельности; в diff
     попадают только реально изменившиеся поля, с парой `from`/`to`;
   - если товар с таким url не менялся ни по одному полю — в diff его не
     включай;
   - если url есть только в текущем прогоне — это товар, добавленный в
     отслеживание (`status: "added"`);
   - если url есть только в предыдущем прогоне — товар убрали из списка
     (`status: "removed"`).
6. Полученный на шаге 5 diff — «сырой»: он содержит вообще все различия,
   включая незначительные колебания цены (например, на доли процента).
   Прежде чем показывать diff пользователю, примени к нему правила
   значимости из `KNOWLEDGE.md` (порог изменения цены, трактовка
   появления/исчезновения скидки и рассрочки, добавленных/пропавших
   товаров) и получи итоговый diff — только то, о чём действительно стоит
   уведомить. Незначимые изменения (порог не пройден) в итоговый diff не
   попадают; если у товара в `changes` не осталось ни одного значимого
   поля — товар целиком выпадает из итогового diff.

Формат diff (как сырого, так и итогового после фильтрации по
`KNOWLEDGE.md` — структура одна и та же, отличается только набор
элементов/полей) — список объектов, по одному на товар с изменениями:

```json
[
  {
    "id": "xbox-wireless-controller-doom-dark-ages",
    "url": "https://www.jib.co.th/web/product/readProduct/76835/...",
    "status": "changed",
    "changes": [
      { "field": "sale_price", "from": null, "to": 2290 }
    ]
  },
  {
    "id": "new-item-slug",
    "url": "https://www.jib.co.th/web/product/readProduct/.../...",
    "status": "added"
  }
]
```

Если итоговый (отфильтрованный по `KNOWLEDGE.md`) diff получился пустым —
это валидный результат двух разных ситуаций, различай их в ответе:
предыдущего прогона не было вовсе («первый прогон, сравнивать не с
чем») или прогон был, но все различия оказались незначимым шумом
(«изменений, о которых стоит уведомить, нет»).

## Сохранение прогона в tracker-data через GitHub MCP

Выполняется после расчёта diff. Репозиторий и ветка фиксированы: owner
`zxvfc`, repo `tracker-data`, branch `main`. Запись — это обычный вызов
GitHub MCP, который сам создаёт коммит на GitHub; локальный `git
clone`/`git push` для этого не нужен и использоваться не должен.

1. Собери JSON-документ по схеме выше и посчитай имя файла
   `YYYY-MM-DD.json` из даты `run_at` (UTC).
2. Проверь, существует ли уже файл с этим именем в репозитории — вызови
   `mcp__github__get_file_contents` (`owner: "zxvfc"`, `repo:
   "tracker-data"`, `path: "YYYY-MM-DD.json"`).
   - Если файл существует — запомни его `sha` из ответа (он понадобится
     для перезаписи).
   - Если файл не найден (404) — это первый прогон за день, `sha` не
     нужен.
3. Запиши файл вызовом `mcp__github__create_or_update_file`:
   - `owner: "zxvfc"`, `repo: "tracker-data"`, `branch: "main"`;
   - `path: "YYYY-MM-DD.json"`;
   - `content` — JSON-документ из шага 1 (человекочитаемый, с отступами);
   - `sha` — из шага 2, если файл уже существовал (без него обновление
     существующего файла будет отклонено); если файла не было — поле не
     передавай;
   - `message` — короткое сообщение коммита, например `tracker: прогон за
     2026-08-12`.

Это разовый коммит в `tracker-data` на каждый прогон (или перезапись
коммитом поверх файла этого же дня — при повторном запуске в тот же
день).

## Формат результата прогона (ответ пользователю)

Помимо коммита в `tracker-data`, верни пользователю:

1. итоговую таблицу прогона — одна строка на товар, не по одному товару за
   раз:

   | id | name | regular_price | sale_price | has_credit |
   |---|---|---|---|---|
   | asus-dual-rtx5060-8gb-oc | ASUS Dual GeForce RTX 5060 8GB GDDR7 OC Edition | 13500 | null | true |
   | xbox-wireless-controller-doom-dark-ages | Microsoft Xbox Wireless Controller — DOOM: The Dark Ages | 2590 | null | true |
   | logitech-g923-trueforce-racing-wheel | Logitech G G923 TRUEFORCE Racing Wheel (PS/PC) | 12900 | null | true |

2. итоговый (отфильтрованный по правилам значимости из `KNOWLEDGE.md`)
   diff с предыдущим прогоном: список изменений, о которых стоит
   уведомить (или явная отметка «первый прогон, сравнивать не с чем» /
   «изменений, о которых стоит уведомить, нет»);
3. имя файла `tracker-data`, в который записан этот прогон (например,
   `2026-08-12.json`), и имя файла, с которым сравнивали (если сравнение
   было).
